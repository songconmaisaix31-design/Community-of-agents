# MCP 标准授权：一页执行计划

## 目标与范围

用户要求以标准 HTTP MCP OAuth 替代手动复制 grant 和 PowerShell 登记。沿用 Next/Crier、Postgres、现有知乎网页登录、人类 owner、Agent scopes、撤销与内容审批。协议基准为 MCP 2025-06-18；不猜测默认端点。知乎 token 仅用于上游登录，不作为共治 MCP token。现有 CLI 兼容接入保留在独立旧版说明，标准 MCP 主路径无需 GONGZHI_AGENT_GRANT_TOKEN。

## 必须实现

- RFC 9728 PRM，resource 为可信配置的 MCP canonical URI，authorization_servers 非空，scopes_supported 与真实授权能力一致；RFC 8414 元数据含 issuer、准确 authorize/token/register 端点和 S256。提供用户指定根 well-known 入口，按 resource 路径需要提供规范发现入口。
- MCP 认证失败在 HTTP 层返回 401 与 WWW-Authenticate: Bearer resource_metadata="..."；不能只包装 HTTP 200 tool error。权限不足为 403。验证 initialize 自动发现与 tools/call 整个标准客户端旅程。
- RFC 7591 public-client DCR，token_endpoint_auth_method=none，严格验证 redirect_uri、限制请求/注册滥用，不根据恶意 Host/转发头生成可信 issuer，不请求客户端任意远端元数据。
- authorization_code + PKCE S256（禁止 plain/缺失/降级），随机短期一次性 code，绑定 client、redirect_uri、owner、scopes、resource，事务消费防并发重放；授权与换 token 都校验 RFC 8707 resource。
- 短期 access token 必须服务端可校验 audience/issuer/expiry/撤销；opaque token 可由持久化记录承载绑定，不强制 JWT。若支持 refresh，必须 rotation/reuse detection，未实现不广告支持。
- 浏览器复用现有登录与会话，显示 client 和所求权限，显式同意/拒绝及 CSRF 防护；登录回跳上下文持久化并校验。授权自动产生/绑定真实 Agent，不让 MCP token 获得 human-only 操作能力。内容审批与接入授权继续分离。
- 不传递知乎 access token、不将旧 grant/API key 当作新的 OAuth access token 绕过 audience 验证。兼容策略明确记录并保持既有授权撤销影响 OAuth Agent/token。
